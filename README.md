# Виртуальный курьер — эталонное решение и закрытые сценарии

> **ПРИВАТНЫЙ РЕПОЗИТОРИЙ ОРГАНИЗАТОРОВ. Участникам не передавать.**
> Здесь эталонное решение и сценарии финала. Публичная среда — отдельный репозиторий `virtual-courier`.

## Зачем

- доказать, что задание решаемо за отведённое время на каждом закрытом сценарии;
- откалибровать сложность и баллы;
- проверять, что изменения среды ничего не ломают (регрессионный прогон).

## Состав

```
src/solution/                 эталон — пакет того же вида, что у участников
├── scripts/reference_node.py весь алгоритм
├── launch/start.launch.py    запускает reference_node (slam/nav по умолчанию выключены)
└── config/                   конфиги из заготовки (эталону не нужны, оставлены для совместимости)
scenarios/final_*.yaml        закрытые сценарии финала
run.sh                        запуск эталона с окнами / записью bag
docs/Регламент_*.docx         регламент (черновик с пометками «[уточнить]»)
tools/build_regulation.py     титул, оглавление и колонтитулы для docx, выгруженного из Claude Docs
```

## Алгоритм

1. **Локализация:** путь — по энкодерам (`/odom`), курс — с IMU (без дрейфа). Это точнее
   slam_toolbox: тот «проскальзывает» вдоль длинных одинаковых коридоров и теряет до 1 м.
2. **Карта:** собственная сетка log-odds по `/scan` (0.05 м), планирование — на сетке 0.1 м
   с раздуванием препятствий на радиус робота + 12 см (при неудаче — + 3 см).
3. **Сетка ячеек:** старт — центр ячейки, курс кратен 90° (п. 4.6 регламента), поэтому центры ячеек
   в кадре карты — точки (2i, 2j). Границы полигона 8×8 выводятся из уже увиденных ячеек и стены выгрузки.
4. **Старт:** разворот на 360° и поиск ArUco №0 — направление стены выгрузки.
5. **Исследование:** BFS по графу ячеек (рёбра — по карте: стена / проход / неизвестно) до ближайшей
   ячейки, пол которой камера ещё не видела.
6. **Станции:** ArUco 1–3 через `estimatePoseSingleMarkers` (сторона 0.18 м): центр станции — в 1 м от
   маркера вглубь полигона; плюс цветной пол станции с близкой дистанции (меньший вес). Голоса
   накапливаются по ячейкам, оценка уточняется на подъезде.
7. **Погрузка:** заезд в центр станции, ожидание груза до 6 с; нет груза — станция неактивна.
8. **Доставка:** все грузы — одним рейсом; в центре старта разворот кормой к стене выгрузки,
   задний ход до 0.6 м от стены, наклон лотка 1.0 рад.
9. **Движение:** A* + pure pursuit (до 0.55 м/с, с грузом 0.45 м/с, поворот до 1.2 рад/с),
   стоп по лидару, выход из застревания.

| Сценарий | Активных станций | Баллы | Максимум | Время | Касания |
|---|---|---|---|---|---|
| public_1 | 3 | 183 | 195 | 308 с | 1 |
| public_2 | 2 | 132 | 145 | 401 с | 0 |
| final_1 | 3 | 184 | 195 | 280 с | 1 |
| final_2 | 2 | 132 | 145 | 387 с | 0 |
| final_3 | 1 | 81 | 95 | 427 с | 0 |

Время на `final_3` большое: единственная активная станция найдена рано, но робот обязан
проверить и две неактивные (заранее их число неизвестно), а лабиринт почти без обходных путей.

## Быстрый запуск с окнами (Webots + RViz + камера)

```bash
./run.sh                    # final_1 с окнами
./run.sh public_2           # публичный сценарий
./run.sh final_3 --bag      # + запись всех топиков в bags/ (zstd, ~5 МБ/мин)
./run.sh final_2 --headless # без окон
./run.sh --list             # доступные сценарии
```

Скрипт сам выдаёт контейнерам доступ к X-серверу (`xhost +SI:localuser:root`), берёт среду из
`../virtual-courier` (или `VC_REPO=...`), показывает в терминале события судьи и смену режимов эталона;
Ctrl+C — остановить всё. В RViz: карта эталона, лидар, путь, осмотренные ячейки, найденные станции и их статус,
текущая цель, зона выгрузки и строка состояния над роботом.

## Зачётный прогон эталона

Из каталога публичного репозитория `virtual-courier`:

```bash
SCENARIO_DIR=~/Programming/virtual-courier-reference/scenarios WEBOTS_GUI=true \
  tools/run_eval.sh reference ~/Programming/virtual-courier-reference - final_1 1
```

(`run_eval.sh` принимает локальный каталог или git-URL и берёт из него только `src/solution`.)

Отладка: `ros2 launch solution start.launch.py debug_dir:=/some/dir` — раз в 5 с в лог пишется
состояние, в `debug_dir/map.png` — карта с ячейками, а при неудачном планировании — дамп `fail_*.npz`.
**В отладочном режиме узел читает `/referee/state`** (только чтобы сравнить оценку позы с истиной);
в управлении это не используется, а на зачётном прогоне `debug_dir` пуст.
